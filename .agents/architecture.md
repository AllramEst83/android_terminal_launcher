# Architecture

Goal: a terminal-style Android launcher. Input line → tokenizer → command registry → command → output lines.
Later phases (aliases, quotes, `&&` chains, history, macros) must be additive, **not** rewrites.

## Layers (dependency direction: UI → terminal → services → platform)

```
lib/
  main.dart                    # runApp only + DI wiring
  app.dart                     # MaterialApp, theme
  terminal/                    # pure Dart (see the foundation exception in Decisions)
    command.dart               # Command, CommandContext
    command_result.dart        # CommandResult (sealed): output / failure / clear
    command_registry.dart      # register / lookup by name + alias; fromProviders
    command_provider.dart      # CommandProvider: a named group of commands + its service
    tokenizer.dart             # String -> ParsedInput (parsed_input.dart)
    app_matcher.dart           # matchApps (open) + rankApps (suggestions)
    suggester.dart             # input line -> List<Suggestion>; suggestion.dart
    log_line.dart              # LogLine + LogKind (input/output/error)
    terminal_session.dart      # ChangeNotifier: log lines, submit(input)
    commands/                  # one file per command + commands.dart (built-in providers, defaultCommands)
    providers/                 # providers that need a service built in main.dart (appearance, notes, info)
    tools/                     # pure helpers behind commands: expression.dart (calc), units.dart (convert), weather_text.dart, calendar_text.dart (day/week/month layout), calendar_dates.dart (date words), contact_matcher.dart (name matching, number detection)
    number_format.dart         # formatNumber: whole numbers plain, float noise rounded away
  services/                    # abstractions over the platform
    app_info.dart              # AppInfo(label, packageName)
    app_repository.dart        # abstract: list launchable apps, launch(packageName)
    app_repository_exception.dart
    android_app_repository.dart# MethodChannel implementation; caches, sorts, excludes self
    local_store.dart           # abstract: read/write/delete JSON values by key
    local_store_exception.dart
    shared_preferences_local_store.dart  # the only file that knows shared_preferences
    entry.dart, entry_store.dart # numbered notes/todos on a LocalStore (serialised calls)
    theme_choice.dart, theme_settings.dart, theme_controller.dart  # theme enum, what commands may do, ChangeNotifier the app listens to
    http_fetcher.dart, io_http_fetcher.dart, network_exception.dart  # the only way features go online (dart:io, no package)
    text_tv.dart, currency_rates.dart, weather.dart  # one service per online feature, all on HttpFetcher
    tv_mosaic.dart             # Text TV block graphics: picture hash -> lit sixths
    styled_text.dart, text_tv_html.dart  # coloured text runs (StyledRun, TvColor); texttv.nu's HTML -> styled rows
    permission_service.dart, android_permission_service.dart  # runtime permissions (AppPermission -> granted/denied/permanentlyDenied)
    location_service.dart, android_location_service.dart      # where the phone is; asks permission itself
    calendar_service.dart, android_calendar_service.dart      # events from the phone's calendars (read-only so far)
    contacts_service.dart, android_contacts_service.dart      # the phone book (read-only); phone_service.dart, android_phone_service.dart  # placing calls; sms_service.dart, android_sms_service.dart  # texts
  ui/
    terminal_screen.dart
    terminal_log.dart          # reversed ListView pinned to the newest line
    prompt_input.dart          # TextField + focus handling + owns suggestion state
    suggestion_bar.dart        # tappable strip above the prompt
    tv_row.dart                # one coloured grid row drawn cell by cell (Text TV)
    block_view.dart, block_card.dart  # rich blocks: dispatch, shared frame and dim constants
    month_view.dart, agenda_view.dart, weather_view.dart, help_view.dart # the calendar card, the agenda, the weather card, the help cards
    notice_view.dart, result_view.dart, choice_view.dart, entries_view.dart, contacts_view.dart # acknowledgements, one big answer, things to pick, notes/todos, people
    block_styles.dart          # BlockStyles and BlockChip shared by every card
    prompt_filler.dart         # lets a button in a card put a command in the prompt
    weather_icon.dart          # the sky as a line drawing, in code
    readable_color.dart        # lift a colour until it shows on the theme
    rocket_art.dart, ascii_banner.dart  # the startup rocket
    double_space_formatter.dart  # double space -> ". " in the prompt
    theme.dart
  messages.dart                # user-facing strings
test/  # mirrors lib/; fakes/ holds FakeAppRepository
```

## Rules
1. **`terminal/` imports no Flutter and no platform code.** It depends on `services/` only through abstract interfaces passed in (constructor injection). This is what makes it fully unit-testable.
2. **Commands are data + a function**: `Command(name, aliases, description, usage, run)`. `help` is generated from the registry, never hand-maintained.
3. **Command results are values, not side effects.** `run` returns a `CommandResult` (sealed: output lines, error, clear-log signal). The session applies it to the log. Commands do not touch the UI.
4. **The tokenizer is its own unit** with a stable output type (`ParsedInput`). Quoting, aliases and chaining get added inside/around it in later phases; the registry and commands don't change.
5. **Platform access goes through `AppRepository`.** Fake it in tests. Swapping the underlying package/channel must touch exactly one file.
6. **Dependency injection by constructor**; wire everything in `main.dart`. No service locators or singletons/globals.
7. **Widgets only render `TerminalSession` state and forward input to it.** No parsing or app-launching in widgets.
8. Cache the installed-app list in the repository/session (with an explicit refresh, and refresh on package install/uninstall later); don't re-query the OS on every keystroke.
9. Matching for `open <app>`: case-insensitive; exact name match wins, then prefix, then substring. If several match, list them and don't guess.

## Adding a command
1. New file in `terminal/commands/`, added to a provider's `commands` list (see below).
2. Unit test in `test/terminal/commands/`.
3. Verify it shows up in `help` with usage text.
No changes to tokenizer, session, or UI should be needed. If they are, the abstraction is leaking; fix that first.

## Adding a feature (provider)
A feature that needs its own service (notes, calendar, weather, …) is a `CommandProvider`:
1. Define the service as an abstract interface in `services/` (implementation in its own file, fake in `test/fakes/`).
2. `XProvider(this._service)` implements `CommandProvider`; its `commands` close over the service. Commands stay data plus a function and still return `CommandResult`s.
3. Add it to `defaultProviders` or, when it needs a service built in `main.dart`, to the list passed to `CommandRegistry.fromProviders` there.
4. Test the commands with the fake service; the registry rejects name clashes across providers, so a clash fails at startup.
`CommandContext` does not get a field per feature.

## Decisions log
Record decisions that future agents can't derive from code (append, newest last):
- State management: plain `ChangeNotifier`; no package. (Revisit only if multiple screens/shared async state appear.)
- App access: hidden behind `AppRepository` because `device_apps` is discontinued (see the archived plan changelog in `archive/plan-through-phase-9.3.md`).
- Launch theme is always black (`Theme.Black.NoTitleBar`, black window background), independent of OS dark mode, so a launcher never flashes white on start.
- Manifest keeps both a `HOME` filter (default-launcher role) and a `LAUNCHER` filter (drawer icon, `flutter run`). Consequence: `AppRepository` must exclude our own package from `list`/`open`.
- `terminal/` imports no widgets or platform code. The one exception is `terminal_session.dart`, which imports `package:flutter/foundation.dart` for `ChangeNotifier`.
- No custom blinking-cursor widget: the `TextField`'s own caret blinks and is themed, so there is no timer/`AnimationController` to dispose.
- Our own package is excluded in Dart (`AndroidAppRepository(ownPackage:)`), not in Kotlin, so it is unit-tested. `main.dart`'s `_appId` must match `applicationId`.
- `open` joins all args with spaces (`open google chrome`) until quoting exists. Unknown-command errors name the command word, not the whole line.
- The log is a `reverse: true` `ListView`, which pins it to the newest line without a `ScrollController`.
- Suggestions fill the input, never run it, so args can be added first. Command names are suggested by the `Suggester`; arguments come from the command's own optional `argSuggestions`, so the suggester never special-cases a command. A new command that wants argument suggestions sets that field.
- Font: JetBrains Mono (Regular + Bold, OFL) bundled under `fonts/`; family name `JetBrainsMono`. No runtime font downloads.
- `TerminalSession` never lets a command or suggester failure escape: `submit` catches `Object` (so `Error`s too) and logs an error line; `suggest` returns nothing on failure. After a failed app-list load, `suggest` skips the platform for 5 s (injectable clock) rather than re-querying on every keystroke; the first success clears it.
- Quoting lives entirely in `Tokenizer`. A word opens a quote (`"` or `'`) only at its start, so a mid-word apostrophe (`open McDonald's`) stays literal and needs no quoting. An unclosed quote sets `ParsedInput.hasUnterminatedQuote` and the session prints an error instead of running a guess. `Suggester` still works on the raw line and offers unquoted completions, which `open`/`uninstall` accept because they join args with spaces.
- Providers, not context fields: a feature's service is captured by its commands' closures. `CommandContext` keeps only what every command or the suggester needs (`apps`, `commands`, `now`, `args`). The built-in commands are grouped as `SystemProvider` and `AppsProvider` (stateless, const); `defaultCommands` is derived from `defaultProviders`. Moving `apps` out of the context into `AppsProvider` was left for later because the suggester needs the app list too.
- `LocalStore` is the only persistence features use: JSON values under string keys, each feature owning its keys (e.g. `theme`, `notes`). Backed by `shared_preferences` (async API, one JSON string per key), which suits settings and personal-scale notes; if data ever outgrows it (search, thousands of rows), replace `SharedPreferencesLocalStore` with a database-backed one, since nothing else knows the package. Reads return fresh copies, unreadable data throws `LocalStoreException` instead of being treated as empty (so a bad value is never silently overwritten), and a missing key is `null`. Tests share `test/services/local_store_contract.dart`, run against both the real store and `InMemoryLocalStore`, so the fake can't drift.
- Themes: `ThemeChoice` (dark, light, coffee) lives in `services/`; `ui/theme.dart` maps it to colours with an exhaustive `switch`, so a theme can't exist without a palette. Only background, text and error colours are defined; cursor, suggestion borders and block separators derive from them, so new UI must use `Theme.of(context).colorScheme`, never a hardcoded colour. Status/navigation bars follow the theme through an `AnnotatedRegion` in `App`. The choice is saved under `theme` and loaded in `main()` before the first frame. The native launch screen stays black in every theme, so the light theme appears after Flutter's first frame.
- `EntryStore` serialises every call (a future queue) because the UI does not await `submit`: two quick `note add` lines would otherwise both read the list and lose one. It refuses stored data that isn't a list of entries instead of treating it as empty, so it never overwrites what it can't read. Ids never repeat, even after removal. Notes and todos are two instances with different keys, so their numbering is independent.
- Log block separation (`ui/terminal_log.dart`): an input line after other lines gets a faint divider above it; output and errors after the first command get a thin left rule. The banner (lines before any input) stays plain. Derived from the log's line kinds, so the session model is unchanged.
- `calc`/`convert` accept `,` as a decimal mark (Swedish keyboards), so functions take one argument only. `convert` uses US customary volumes plus Swedish `krm`/`tsk`/`msk`, decimal `kb` (1000) and binary `kib` (1024).
- Networking: features reach the network only through `HttpFetcher` (`IoHttpFetcher` on `dart:io`: 10 s timeout that also covers stalled transfers, 2 MB cap, redirects followed, HTTPS only so no cleartext exception is needed). Every failure is a `NetworkException` whose message names the host and is printed as-is by the command. Services are concrete classes over `HttpFetcher`; tests give them a `FakeHttpFetcher` that fails on any request nothing routed, so a test must state what code is expected to ask for. The only request that carries anything about the user is a place name typed to `weather`.
- Test fixtures under `test/fixtures/` are real API responses (reduced to the fields we read). When an API changes, re-fetch it, replace the fixture, and let the parser tests show what broke. Values in tests come from the fixture, not from memory.
- Offline: currency rates are the one online feature with a saved copy (`LocalStore` key `currency.rates`, 6 h fresh, older copy used when the network fails and labelled so). The saved copy is disposable, so unlike notes a damaged one is replaced rather than refused. A saved rate dated in the future (bad clock) is not trusted. Text TV and weather are live data and just report the failure.
- Text TV: 40-column pages from texttv.nu (Inrikes 101, Utrikes 104, Sport 300, Väder 400; the API asks each client to send a unique `app` value). `content_plain` is a list, one entry per sub-page; an unknown page is `[]`, a page that is not in broadcast is one line saying so, both mean "not in broadcast".
- Fixed-width grids: `CommandOutput(columns: n)` marks lines as a grid `n` characters wide; the log scales the font (same scale for every line) to fill the available width in both directions — down on a narrow screen so a wide grid doesn't wrap, up to `gridUpscaleLimit` (`ui/terminal_log.dart`) on a wide one so a page doesn't sit at native size with the screen mostly blank — and renders it without the ordinary block's left rule, edge to edge like its own screen. Blank lines render as a space so they keep their height. Use it for anything column-aligned (Text TV now, calendar month view later).
- `help` has three layers (overview by provider, group, command) because a phone shows ~36 columns. Providers double as help groups (`CommandRegistry.groups`). Commands may set `forms`, `examples`, `notes`; a test requires every help line to fit 36 columns and every description to fit the group view, so new commands must keep lines short. Overviews put the hint on the last line, since the log is pinned to the bottom.
- `ToolsProvider` needs the currency service, so it is built in `main.dart`; `defaultProviders` is only what needs nothing but the app list (system, apps).
- Font size: `FontSizeChoice` (small, normal, large, huge) lives in `services/`, saved under `fontSize` next to `theme`, next to the same `AppearanceProvider`/`FontSizeController` pattern as themes. `ui/theme.dart` maps each choice to a `fontSizeFactor` (an exhaustive `switch`, so a choice can't exist without a scale) applied via `TextTheme.apply`, so it scales every text style at once — the log, prompt and suggestion bar all move together, and fixed-width grids stay correctly proportioned since `_GridText` reads its base size from the already-scaled theme. Steps mirror Android's own font-scale options so they land where a user expects. `App` now listens to `Listenable.merge([themes, fontSize])`.
- Startup/`clear` banner: `TerminalSession` keeps the banner strings it was constructed with and re-appends them (as `LogKind.banner` lines) after every `clear`, not just once at startup, so the screen is never truly empty. `ui/terminal_log.dart` renders a `banner` line as `AsciiBanner` (`ui/ascii_banner.dart`) instead of through `_LogLineView`, so the ordinary `input`/`output`/`error` style `switch` stays exhaustive over exactly those three. `AsciiBanner` blinks a small ASCII cat a couple of times on its own `Timer` and then stops — deliberately finite, not a looping animation, because this sits on a launcher's home screen that can stay on-screen for hours and an endless repaint would only cost battery.
- Runtime permissions: features never name an Android permission. `AppPermission` (in `services/permission_service.dart`) names a capability; `PermissionsChannelHandler.kt` holds the only table mapping it to manifest strings, so a new capability is one enum value plus one table row (and the manifest line). `PermissionService.request` never throws; `permanentlyDenied` (no dialog will appear any more) is decided in Kotlin from `shouldShowRequestPermissionRationale` after a refusal, so Dart keeps no record of denials that Android already tracks. A feature that needs a permission wraps it in its own service (`LocationService` asks first, then queries) and the command only prints what came back; when the answer is permanent it prints where to switch the permission on instead of asking again. `MainActivity` must forward `onRequestPermissionsResult` to the handler.
- Location: coarse only (`ACCESS_COARSE_LOCATION`, network provider, 15 s limit on the Kotlin side plus a Dart guard), because a forecast doesn't need more and the permission dialog is less alarming. Plain `weather` uses it and falls back to the saved home city; `weather <city>` and `weather home ...` never touch it. Open-Meteo has no reverse geocoding, so the place is labelled "Current location".
- Calendar: events come from `CalendarContract.Instances` (so repeats are already expanded) and cross the channel as raw epoch milliseconds; **all turning of times into local `DateTime`s happens in Dart** (`AndroidCalendarService`) where it is tested. An all-day event is a *date* stored as UTC midnight with an exclusive end, so it is converted by its UTC y/m/d, never as an instant, or it would slide a day east of Greenwich. Every event is a half-open local range; the service asks for a day either side of the range and filters after conversion for the same reason. Calendar days are added with `DateTime(y, m, d + n)`, never `+ Duration(days: n)`, so a daylight-saving change can't move an event to 23:00. The month view is a fixed-width grid (`monthGridColumns` = 28); day and week views are ordinary lines because titles are long and should wrap.
- Contacts and calls: the channel returns one raw row per phone number and Dart does everything else (`AndroidContactsService` merges same-name entries and de-duplicates numbers by digits; `matchContacts` ranks names), because case-insensitive matching of åäö is wrong in SQLite `LIKE` and a phone book is small. `call` must never ring by guess: it rings only when exactly one person matches and that person has one number or exactly one mobile; otherwise it lists. `PhoneService.call` treats `CALL_PHONE` as optional: refused, permanently refused, or an emergency number (Android throws `SecurityException` for those from ordinary apps) all end in `ACTION_DIAL`, and the command reports "dialer opened" as normal output, not an error. `call <number>` never touches contacts. Providers may share a help group by returning the same `name` (`CalendarProvider` and `PhoneProvider` are both "personal"): `CommandRegistry` files commands by that name, and one group per provider had pushed the help overview past its 16-line test.
- SMS: an irreversible action, so the command is strict where `call` is forgiving. `SmsChannelHandler` completes only when Android's per-part "sent" broadcast has arrived OK for every part (unique action per send so two in flight can't mix; the receiver is released on completion, timeout or dispose); a timeout is an error that warns against blind resending, not a success. `sms` takes exactly two arguments and never infers where an unquoted name ends. Recipient resolution (`resolveRecipient`) is shared with `call`: a person is chosen only when exactly one matches and has one number or one mobile; a command supplies its own `numberHint`/`pickHint` last lines. `SEND_SMS` has no fallback: a refusal is reported as such.
- Coloured grids: `CommandOutput.styles` (one `List<StyledRun>` per line, `plainText(styles[i]) == lines[i]`) rides beside `columns`; the session keeps it only when it lines up one to one, and the UI draws a line that has runs with `TvRow` instead of `Text`. `TvRow` paints cell by cell (backgrounds overlap by half a pixel so rows and bars have no seams; per-cell text so ligatures never join neighbours) on the fixed teletext palette (`tvColorOf`), never the theme's colours: a teletext page is its own black screen, since white and yellow vanish on a light theme. Scale is decided once for the whole grid width like plain grids. The black screen has a gutter of 0 cells on the left and 1 on the right (`tvGutterLeftCells`/`tvGutterRightCells`): the site's pages already leave column 0 blank, so that blank column is the left margin and the visible margins come out equal. Fitting, painting and tap positions all include the gutters. A tall run (`StyledRun.tall`) makes the row twice as high with the picture stretched vertically. Text TV keeps plain text as the source of truth: `TextTvPage.styledParts` is null whenever the HTML is missing or unexpected (a row not 40 wide, wrong part count), so a change on the site costs the colours, not the page. The parser matches `class` anywhere in a tag (the site puts `style` first on double-height rows). Block graphics (`bgImg` cells) are `StyledRun.mosaic` patterns: `services/tv_mosaic.dart` regenerates every picture texttv.nu can draw (a standard GIF encoder reproduces its files byte for byte) and looks up the CRC-32 in the picture address; an unknown picture is a blank cell in the span's colours. Links are `StyledRun.command`s (`texttv <page>`) that `TvRow` runs through `onRun`; the footer's prev/next are built the same way.
- Prompt habits: `periodOnDoubleSpace` (pure, `terminal/tools/double_space.dart`) ends a sentence on a double space but only after at least two words, so a command word is never given a period; `ui/double_space_formatter.dart` only wraps it. Autocorrect stays off because it would mangle commands.
- Startup banner is finite (rocket: ignition, climb, settle; about 1.8 s) for the same battery reason as the cat before it. All frames are equal-width plain ASCII so the picture can be centred as one block.
- App icon: generated, not hand-placed. `tool/make_app_icon.py` (Pillow) cuts the monitor out of the JPEG and writes the adaptive foreground/background and legacy icons under `android/app/src/main/res`; re-run it if the source art changes. The adaptive foreground keeps the monitor within the safe zone (52 of 108 dp wide).
- Rich blocks: `CommandOutput.block` (`terminal/blocks.dart`, sealed `RichBlock`) is a richer form of the same output. Rules: (1) the command always also returns the plain `lines`, which say the same thing; a block never replaces them. (2) Blocks are pure values with no colours of the theme and no widgets; `ui/block_view.dart` switches over them exhaustively, so a new block type fails to compile until something draws it. (3) Anything tappable is a `command` string the UI feeds to `session.submit`, so a tap can do nothing a typed command cannot, and it shows up in the log as input. (4) `ViewMode` (`ui rich|plain`, persisted) is read by the session as a command finishes: rich keeps the block (one `LogLine`, `text` = plain lines joined), plain logs the lines. Old output is never redrawn. (5) Colours come from the theme (`onSurface`/`surface`, `blockDimAlpha` for secondary text); an outside colour (a calendar's) goes through `readableOn` first. Contrast for every theme and every font size is tested, on a narrow screen.
- The log never changes without an announcement: `TerminalSession` calls `notifyListeners()` after every mutation that a frame could see, including the echo of a command that is about to run (a slow command otherwise leaves the log ahead of what the UI was told), and `TerminalLog` builds from a snapshot of the lines. The list builds children lazily and asks for them later than the build that created it; reading a live list with a length from an earlier build shifts its keyed children and trips `sliver_multi_box_adaptor`'s order assertion. Tapping in a rich block must never be the first thing to notice this: keep both halves.
- Run or fill: a tap in a card either **runs** its command (`RunCommand`, echoed in the log like typed input) or **fills the prompt** with it (`FillPrompt`, through `PromptFiller`, exactly as tapping a suggestion does: the user looks at it, edits it, presses Enter). The rule is about consequences, not about the block: anything that only shows or switches something reversible runs (open an app, a page, a day, `theme coffee`, tick a todo); anything that acts on someone, cannot be undone, or needs more typed **fills** (`call`, `sms` with its opening quote, `note edit` with the current text, `note rm`, `uninstall`, and every option of a "several match" picker for call/sms). Examples in `help` are not tappable at all. A card must never make a call, send a text or delete something by a stray tap.
- Generic blocks, not one per command: `NoticeBlock` (an acknowledgement, with `noticeOutput()`), `ResultBlock` (one large answer), `ChoiceBlock` (chips or rows, grouped, optionally with a current one; used for apps, themes, units, currencies, contact names and every picker), `EntriesBlock`/`EntryDetailBlock`, `ContactsBlock`. A new command should reach for these before adding a block type. `CommandFailure` can carry a block too, for a failure that asks the user to pick; other failures stay plain red lines on purpose.
- Command lines built for taps go through `quoteArg` (`terminal/tools/quote.dart`), tested to round-trip through the `Tokenizer`, so a name with a quote or a space can never break the line. Numbers in call/sms lines are digits only (`dialable`).
